moonkafka — Full-Feature Kafka 4.3.x Driver

moonkafka is an Apache Kafka client driver written in MoonBit, targeting Kafka 4.3.x (first 4.3.0 release: 2026-05-22), KRaft-only, with no ZooKeeper-era or pre-4.0 compatibility.

Status: the transport + data-plane feature set is implemented and covered by a 200+ test suite (unit, mock-broker, golden fixtures) plus an optional real-cluster integration harness. The API may still change before 1.0.

Overview

The project grows moonkafka from a simple producer/consumer into a fully featured Kafka client through a sequence of independently committable phases (0–7). Phases 0–4 are the critical path; 5–7 are breadth and polish. Sources of truth for implementation work:

  • Kafka 4.3 protocol guide
  • Per-API message schemas: clients/src/main/resources/common/message/*.json in the Kafka repo
  • Implementation notes
  • 4.3 release notes for client-visible KIPs (KIP-1274 classic-protocol deprecation phase 1, KIP-1251 assignment epochs, KIP-1258 OAuth client assertions, share-group tuning)

Scope

In scope

  • Complete wire-protocol coverage for everything a client driver needs on a 4.3.x cluster (data plane, group coordination, transactions, admin, ACLs, share groups), at flexible (modern) message versions only.
  • Robust transport: request pipelining, timeouts, retries, reconnection, TLS, SASL (PLAIN, SCRAM-SHA-256/512, OAUTHBEARER), re-authentication, rebootstrap (REBOOTSTRAP_REQUIRED, error 129).
  • Full record handling: RecordBatch v2 with compression (gzip, snappy, lz4, zstd), record headers, transactional/control batches, read-committed filtering.
  • Producer: batching, idempotence, configurable partitioners (murmur2, Kafka-compatible), transactions.
  • Consumer: topic subscriptions (incl. regex), consumer groups via both the KIP-848 new protocol (primary; classic protocol deprecation started in 4.3) and the classic protocol (compat), offset management (commit/seek/autocommit), cooperative + eager rebalancing, pause/resume, seek-by-timestamp.
  • Admin client covering topic/cluster/config/group/ACL/quota/transaction management.
  • Share groups (KIP-932) — consumer-style ShareConsumer.
  • Native backend only (module is preferred_target = "native"; moonbitlang/async sockets are native-only).

Out of scope

  • Kafka < 4.0 brokers, ZooKeeper, message formats v0/v1 (magic < 2).
  • Broker-internal APIs: WriteTxnMarkers, share-group state APIs, AddRaftVoter/RemoveRaftVoter, FetchSnapshot, quorum Vote/BeginQuorumEpoch/EndQuorumEpoch, ControlledShutdown, LeaderAndIsr/StopReplica/UpdateMetadata, ControllerRegistration, BrokerRegistration/BrokerHeartbeat, AllocateProducerIds, Envelope, AlterPartition.
  • KIP-1071 Streams group protocol (StreamsGroupHeartbeat 88, StreamsGroupDescribe 89).
  • Two-phase commit producer (InitProducerId v6 is marked unstable).
  • Full Java AdminClient parity for every exotic operation on day one — admin coverage grows incrementally.

Design decisions

#DecisionSummary
D1Version strategyPer API, implement a small explicit set of versions: the newest every 4.0+ broker accepts plus any older version a feature needs. ApiVersions (v3/v4) negotiation picks the highest mutually supported version from the implemented set; below the implemented floor fails fast with a clear message. Never implement a version purely for pre-4.0 brokers.
D2Hand-written codecsCodecs stay hand-written in MoonBit block style, one file per API key or small group, checked against the Kafka repo's *.json schemas. No JSON-schema code generator; revisit out-of-tree only if the volume proves painful.
D3Tagged fieldsEncoders get a real write_tag_buffer(tags); decoders keep unknown top-level tags where round-tripping is demanded (rare); elsewhere skipping is correct and stays.
D4CompressionDecoder support is mandatory for all four codecs (consumers read whatever producers wrote); producer-side support follows config. Gzip via native FFI to system zlib; snappy (xerial-framed) and lz4 (Kafka's frame variant) are pure MoonBit; zstd via a vendored single-file decompressor. Whole-batch compression only, never per-record.
D5Group protocolsKIP-848 (ConsumerGroupHeartbeat) is first-class and default: broker-side assignment, server-driven. The classic protocol (JoinGroup/SyncGroup/Heartbeat) is implemented for compat with classic groups, eager + cooperative assignment. Config selects; auto prefers consumer.
D6Concurrency modelBuilt on moonbitlang/async tasks: one sender task per producer, one heartbeat task per group member, background autocommit, metadata refresher. Shared state via mutexes/condvars; user-facing calls stay async and cancellation-aware.
D7Error taxonomyBroker failures are BrokerError(code, context) with the full 4.3 error-code table (codes -1–133) backing error_name/error_retriable lookups. Client-side violations stay ProtocolError(String); wire decoding stays DecodeError. Retry policy lives in the client, not the caller.
D8ConfigOne Config struct per client surface (producer/consumer/admin) with librdkafka-style snake_case fields (bootstrap_servers, acks, enable_idempotence, group_protocol, …), validated at connect. No stringly-typed config maps.

Roadmap

Phase 0 — Foundations & housekeeping done

  • Error taxonomy — errors.mbt with the full published 4.3 table (codes −1–133); BrokerError(code, context) suberror with name()/is_retriable().
  • Primitives — murmur2 port verified against all six UtilsTest vectors; Uuid with Java-canonical 22-char base64url formatting.
  • Tagged-field encode — write_tagged_fields writes ascending, plain-uvarint tag buffers.
  • Config structs — CommonConfig (bootstrap parsing, security protocol + SASL shells), ProducerConfig, ConsumerConfig, all validated at construction.
  • Time/backoff helpers — pure backoff_ms, jittered Backoff schedule (±20%), Deadline on @async.now().
  • Package split — buf/ and internal/ subpackages; root surface deliberately shrunk (Encoder/Decoder/crc32c/murmur2 no longer public API).

Phase 1 — Transport hardening done

  • BrokerConnection v2 — pipelining via write-lock + frame-level read-lock + pooled out-of-order responses; per-request timeouts closing the connection; TransportError on EOF/corrupt frames; max in-flight via semaphore.
  • Reconnect & bootstrap set — round-robin bootstrap rotation, failover at dial time, producer/consumer recovery from TransportError and leadership errors with backoff; REBOOTSTRAP_REQUIRED handling.
  • Throttling — every response decoder returns throttle_time_ms; the connection delays subsequent requests.
  • TLS — BrokerStream enum, TlsClientOptions (SNI, custom CA PEM), wired through config for SSL / SASL_SSL.
  • SASL — SaslHandshake v1 + SaslAuthenticate v2; PLAIN, SCRAM-SHA-256/512 (pure MoonBit PBKDF2), OAUTHBEARER via user-supplied token provider; re-authentication tracked.
  • Cluster layer — ClusterClient owns the bootstrap set, connection pool keyed by node id, metadata caching with refresh scheduling, topic-id map (KIP-516), batched FindCoordinator v4 (KIP-699).

Phase 2 — Protocol completeness (data plane) done

  • Version negotiation matrix — per-API floor/ceiling matrix; the handshake parses the broker's ranges into BrokerVersions stored on every connection; choose-highest-common logic with clear no-overlap errors; REBOOTSTRAP_REQUIRED recovery.
  • Metadata — v12/v13 dispatch; topic_id exposure (Fetch v13+); DescribeTopicPartitions v0 with cursor pagination; hardened decoder bounds checks.
  • Produce — v12 (topic names) / v13 (topic-id, KIP-516); per-record record_errors with messages (KIP-467).
  • Fetch — v12–v16; incremental fetch sessions (KIP-227) with eviction/session-restart handling; truncated-batch handling with records_complete.
  • ListOffsets v10/v11 — KIP-1075 timeout, KIP-1023 earliest-pending sentinel; public offset sentinel constants.
  • Record layer — record headers round-trip; detailed batch decode (producer id/epoch, control/transactional flags); collect_committed read-committed primitive; RecordBatchBuilder.
  • Compression — one Codec interface mapped to attribute bits 0–4; snappy (xerial framing) and LZ4 (Kafka frame framing) pure MoonBit; gzip via system zlib FFI; zstd via vendored single-file decompressor; golden fixtures from independent implementations.
  • Decoder robustness — deterministic fuzz over compressed streams, record batches, and five wire decoders: everything raises a decode error or succeeds, never panics.

Phase 3 — Full producer done

  • Partitioner — Murmur2 (default), Murmur2RoundRobin, RoundRobin; sticky partitioner per batch (KIP-794); manual partition override.
  • Batching accumulator — per-partition queues over RecordBatchBuilder; batch_size rotation, linger_ms readiness, buffer_memory accounting with BufferExhausted; per-partition order preserved across coalescing.
  • Sender task — per-producer drain loop in the caller's task group; one Produce request per leader, pipelined up to max_in_flight; acks=0 fire-and-forget; retriable failure requeue with backoff inside delivery_timeout_ms (default 120s).
  • Public API — send, per-record SendHandle (await/cancel), batched send_all, async on_complete callbacks.
  • Idempotence — InitProducerId v5; pid/epoch + per-partition sequence stamping; Java-client reset rules on UNKNOWN_PRODUCER_ID; config validation (acks=-1, max_in_flight ≤ 5).
  • Transactions — coordinator init, begin_transaction/commit_transaction/abort_transaction, AddPartitionsToTxn v3, AddOffsetsToTxn v4 + TxnOffsetCommit v4, EndTxn v5 with epoch adoption (KIP-890); coordinator retry/refind, fencing detection, abort-on-error commit policy.
  • Producer metrics — metrics() with queue depth, in-flight batches, sent/failed counters, throttle hints.

Phase 4 — Full consumer done

  • Offset management — OffsetCommit v8–v10 / OffsetFetch v8–v10; commit/commit_async/committed with coordinator retry; seek family over ListOffsets; background autocommit with commit-on-close.
  • Fetcher — concurrent long-poll per leader through incremental sessions; max_poll_records/max_partition_fetch_bytes caps with rewind; pause/resume; auto_offset_reset policies; KIP-320 truncation detection via OffsetForLeaderEpoch v4; read_committed filtering via collect_committed.
  • KIP-848 member — ConsumerGroupHeartbeat v0/v1; client-generated member ids; server-driven assignment applied atomically around RebalanceListener hooks; static membership; regex subscription (glob subset); graceful leave; fencing recovery.
  • Classic member — JoinGroup v9 / SyncGroup v5 / Heartbeat v4 / LeaveGroup v5; Range, RoundRobin, Sticky, and CooperativeSticky (KIP-429 two-round) assignors; static membership; rebalance listeners.
  • Consumer surface — subscribe/assign split, position/committed/assignment/group_metadata; max_poll_interval_ms enforcement; utf8 record helpers.
  • group_protocol config — KIP-848 (default), classic, or fallback ordering probed against the broker's advertised APIs. Documented interop caveats: mixed-vendor cooperative groups, glob-subset regex, classic UNSTABLE_OFFSET_COMMIT handling.

Phase 5 — Admin client done

  • Admin core — shared retriable-result retry policy; any-broker control connection vs controller-routed ops; per-item error codes as values; paginated DescribeTopicPartitions walking.
  • Topic ops — CreateTopics v7, DeleteTopics v6 (names, ids, mixed), CreatePartitions v3, DeleteRecords v2, OffsetDelete v0.
  • Cluster/config — DescribeCluster v0–v2, DescribeConfigs v4, IncrementalAlterConfigs v1 + AlterConfigs v2, ListConfigResources v0–v1 (KIP-1142), DescribeLogDirs v2–v5, ElectLeaders v2, reassignments, UnregisterBroker v0, DescribeQuorum v2, UpdateFeatures v2.
  • Groups — DescribeGroups v6 (classic only), ConsumerGroupDescribe v1 (KIP-848 members), ListGroups v5, DeleteGroups v2.
  • Producers/transactions — DescribeProducers v0, DescribeTransactions v0, ListTransactions v2.
  • Security — Describe/Create/DeleteAcls v2–v3 with pinned enum byte values; DescribeClientQuotas/AlterClientQuotas v0–v1; Describe/AlterUserScramCredentials v0 with password-derived SCRAM upserts.

Phase 6 — Share groups (KIP-932) & telemetry done

  • ShareConsumer — ShareGroupHeartbeat v1 membership, ShareFetch v2 (acquisition/release, delivery-count caps), ShareAcknowledge v2 (accept/release/reject/renew); Describe/Alter/DeleteShareGroupOffsets admin ops.
  • Telemetry (KIP-714) — GetTelemetrySubscriptions/PushTelemetry client with a pluggable metrics provider.

Phase 7 — Hardening, performance, release done

  • Test harness — Docker compose (KRaft single/multi broker), make integration, in-process fake-broker testkit with fault injection (throttling, version ceilings, SASL/TLS, session churn).
  • CI — GitHub Actions: build + tests, fmt check, moon info clean-diff, Docker Kafka 4.3 integration job, golden-file regeneration.
  • Performance — encoder preallocation, zero-copy-ish decoding (BytesView), benchmark script with bench-produce.
  • Docs & release — README feature matrix, protocol notes, CHANGELOG, version 0.2.0 with release checklist.

Testing strategy

  1. Unit (pure) — codec round-trips with debug_inspect snapshot tests; known-vector tests (murmur2, CRC32C, varints, SCRAM); decoder robustness (truncation must raise, never panic).
  2. Golden files — byte-exact request/response fixtures in test/golden/; decoders must parse them, encoders must byte-match where deterministic.
  3. Mock broker — an in-MoonBit fake broker speaking the real protocol: version ceilings, error injection, throttling, session churn.
  4. Integration — Dockerized apache/kafka:4.3.x (KRaft) covering every phase's acceptance criteria.
  5. Per AGENTS.md: moon info && moon fmt and .mbti diff review every commit; coverage reviewed at phase end.

Risks & open questions

  • AddPartitionsToTxn v4/v5 shape — KIP-890 reshaped this API; resolved by spiking what the Java 4.x producer negotiates (client shape, v3).
  • zstd via C FFI — resolved: the zstd single-file decompressor is vendored; gzip links the universally present system zlib.
  • moonbitlang/async maturity — long-lived background tasks + cancellation semantics for heartbeat/sender loops; close-under-load covered by mock-broker tests.
  • Classic vs KIP-848 parity — regex subscription for classic groups is client-side and works differently from 848's server-side regex; documented rather than force-unified.
  • SCRAM pure-MoonBit crypto — spiked: moonbitlang/x provides sha256/sha512 + HMAC, so SCRAM needs only a thin PBKDF2 loop; no C FFI.
  • Client-side CSPRNG for member ids — resolved with a clock-seeded uuid-hex scheme; format-only uuid remains a note.
  • Kafka 4.3.x point releases — may bump max API versions; the negotiation matrix makes that a non-event, but golden files should be regenerated per minor release.
