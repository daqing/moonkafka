moonkafka — 全功能 Kafka 4.3.x 驱动

moonkafka 是一个用 MoonBit 编写的 Apache Kafka 客户端驱动，面向 Kafka 4.3.x（4.3.0 首发于 2026-05-22），仅支持 KRaft 模式，不兼容 ZooKeeper 时代及 4.0 之前的版本。

状态：传输层 + 数据面特性已实现，并有 200+ 测试 （单元、模拟 broker、golden fixture）以及可选的真实集群集成测试套件作为保障。 在 1.0 之前 API 仍可能调整。

概览

本项目的目标是将 moonkafka 从简单的生产者/消费者逐步演进为功能完备的 Kafka 客户端驱动。整体规划分为 0–7 共八个阶段，每个阶段均由可独立提交的 工作项组成并有验收标准；阶段 0–4 是关键路径，5–7 属于广度与打磨。实现工作 的权威依据：

  • Kafka 4.3 协议指南
  • 各 API 的消息 schema：Kafka 仓库中的 clients/src/main/resources/common/message/*.json
  • 实现说明
  • 4.3 版本发布说明中对客户端可见的 KIP（KIP-1274 经典协议弃用第一阶段、 KIP-1251 分配纪元、KIP-1258 OAuth 客户端断言、共享组调优）

范围

属于范围内

  • 完整覆盖 客户端驱动 在 4.3.x 集群上所需的线协议 （数据面、组协调、事务、管理、ACL、共享组），只使用 flexible（现代）消息版本。
  • 健壮的传输层：请求流水线、超时、重试、重连、TLS、SASL （PLAIN、SCRAM-SHA-256/512、OAUTHBEARER）、重新认证、重新引导 （REBOOTSTRAP_REQUIRED，错误码 129）。
  • 完整的记录处理：RecordBatch v2 及压缩（gzip、snappy、lz4、zstd）、 记录头、事务/控制批次、read_committed 过滤。
  • 生产者：批处理、幂等、可配置分区器（Kafka 兼容的 murmur2）、事务。
  • 消费者：主题订阅（含正则），通过 两条路径 加入消费组 —— KIP-848 新协议（主路径；4.3 起经典协议进入弃用流程）和经典协议（兼容）； 偏移量管理（提交/seek/自动提交）；协作式 + 急切式再均衡；暂停/恢复； 按时间戳 seek。
  • Admin 客户端，覆盖主题/集群/配置/消费组/ACL/配额/事务管理。
  • 共享组（KIP-932）—— 消费者风格的 ShareConsumer。
  • 仅原生后端（模块为 preferred_target = "native"； moonbitlang/async 的 socket 仅支持原生目标）。

不属于范围

  • Kafka 4.0 之前的 broker、ZooKeeper、消息格式 v0/v1（magic < 2）。
  • broker 内部 API：WriteTxnMarkers、共享组状态 API、 AddRaftVoter/RemoveRaftVoter、 FetchSnapshot、仲裁 Vote/BeginQuorumEpoch/EndQuorumEpoch、 ControlledShutdown、LeaderAndIsr/StopReplica/UpdateMetadata、 AllocateProducerIds、Envelope、AlterPartition 等。
  • KIP-1071 Streams 组协议（StreamsGroupHeartbeat 88、 StreamsGroupDescribe 89）。
  • 两阶段提交生产者（InitProducerId v6 被标记为 unstable）。
  • 第一天就追求与 Java AdminClient 在所有冷门操作上的完全对等 —— admin 覆盖面是渐进扩展的。

设计决策

#决策要点
D1版本策略每个 API 只实现一小段显式版本区间：所有 4.0+ broker 都接受的最新版本，加上特性所需的更老版本。ApiVersions（v3/v4）协商在已实现集合内选择双方共同支持的最高版本；低于实现下限时快速失败并给出清晰报错。绝不单纯为 4.0 之前的 broker 实现某个版本。
D2手写编解码器编解码器保持 MoonBit 块风格手写，每个 API key（或小组）一个文件，与 Kafka 仓库的 *.json schema 逐字段核对。明确不采用 JSON schema 代码生成器；若工作量大可再考虑树外生成器。
D3标记字段编码器具备真正的 write_tag_buffer(tags)；仅在少数需要回传的场景保留未知顶层标记，其余场景一律跳过。
D4压缩四种编解码器的解码支持是强制的（消费者必须能读任何生产者写的内容）；生产者侧按配置启用。gzip 通过系统 zlib 原生 FFI；snappy（xerial 分帧）与 lz4（Kafka 帧变体）为纯 MoonBit 实现；zstd 通过内嵌的单文件解压库。压缩始终按整个批次进行。
D5组协议KIP-848（ConsumerGroupHeartbeat）是一等公民且为默认：broker 端分配、服务端驱动。经典协议（JoinGroup/SyncGroup/Heartbeat）仍实现以兼容固定 classic 的集群/组，支持急切与协作式分配。由配置选择；自动模式优先 consumer 协议。
D6并发模型基于 moonbitlang/async 任务：每个生产者一个 sender 任务、每个组成员一个心跳任务、后台自动提交任务、元数据刷新任务。共享状态用互斥锁/条件变量；对外 API 保持异步并遵循取消语义。
D7错误分类broker 报告的失败为 BrokerError(code, context) 子错误，背后是完整的 4.3 错误码表（-1–133）支撑 error_name/error_retriable 查询。客户端侧违规仍是 ProtocolError(String)；线解码错误为 DecodeError。重试策略在客户端内部。
D8配置每个客户端面（生产者/消费者/admin）一个 Config 结构体，字段为 librdkafka 风格的 snake_case（bootstrap_servers、acks、enable_idempotence、group_protocol 等），连接时校验。不使用字符串型配置表。

              组成员（848 + 经典）、分配策略

公共 API 保留在根包（@moonkafka.Producer、 …Consumer、…Admin、…ShareConsumer）， 内部实现为子包。每个阶段以 moon info && moon fmt 和 .mbti 差异审查收尾。

协议覆盖面（Kafka 4.3）

每个 API 按下限（驱动至少实现的版本 —— 所有 4.0+ broker 均接受）到 4.3 上限 实现。API key 数字在实现该编解码器时才 从 4.3 协议指南 / message/*.json schema 中固定下来，绝不凭记忆。 部分要点：

API4.3 上限我们实现的下限说明
Produce13v12（主题名）+ v13（topic-id）从 v11 升级
Fetch18v12（名字）+ v13–v16（topic-id、增量会话、节点端点）v7 起会话为强制
ListOffsets11v10/v11（新增 timeout_ms）
Metadata13v12 + v13（顶层 error_code）
DescribeTopicPartitions0v0分页、游标式；admin 与正则订阅使用
OffsetCommit / OffsetFetch10v8–v10v9 携带 KIP-848 成员身份
FindCoordinator6v4（批量 coordinator_keys）KIP-699
InitProducerId6v5v6 = 2PC，unstable —— 跳过
ConsumerGroupHeartbeat1v1（新增 subscribed_topic_regex）KIP-848 —— 主消费组协议
经典组管理JoinGroup v9、SyncGroup v5、Heartbeat v4、LeaveGroup v5、DescribeGroups v6、ListGroups v5兼容路径
Admin 系列CreateTopics v7、DeleteTopics v6、DescribeCluster v2、DescribeConfigs v4、IncrementalAlterConfigs v1、ACL v2–v3、配额 v0–v1、SCRAM 凭证 v0、DescribeQuorum v2、UpdateFeatures v2 等逐项错误码以值返回

范围外broker/控制器内部 API（见"范围"）—

错误码：4.3 的完整错误码表（−1 至 133）已在 protocol/errors.mbt 中实现，每项带 name、retriable 以及致命性 / 需刷新元数据等标志。

路线图

阶段 0 —— 地基与整理 已完成

  • 错误分类 —— errors.mbt 含完整 4.3 错误码表（-1–133）；BrokerError(code, context) 子错误带 name()/is_retriable()。
  • 基础类型 —— murmur2 移植，全部六个 UtilsTest 向量通过；Uuid 采用 Java 规范的 22 字符 base64url 格式。
  • 标记字段编码 —— write_tagged_fields 以升序普通 uvarint 写标记缓冲。
  • 配置结构体 —— CommonConfig（引导服务器解析、安全协议 + SASL 外壳）、ProducerConfig、ConsumerConfig，均在构造时校验。
  • 时间/退避工具 —— 纯函数 backoff_ms、带 ±20% 抖动的 Backoff、基于 @async.now() 的 Deadline。
  • 包拆分 —— buf/ 与 internal/ 子包；根包 API 面有意收缩。

阶段 1 —— 传输层加固 已完成

  • BrokerConnection v2 —— 写锁 + 帧级读锁 + 乱序响应池实现流水线；单请求超时关闭连接；EOF/坏帧抛 TransportError；信号量限制最大在途请求。
  • 重连与引导集合 —— 引导服务器轮询，拨号时故障转移，生产者/消费者从 TransportError 和领导权错误中恢复；处理 REBOOTSTRAP_REQUIRED。
  • 限流 —— 每个响应解码器返回 throttle_time_ms；连接延迟后续请求。
  • TLS —— BrokerStream 枚举、TlsClientOptions（SNI、自定义 CA），支持 SSL / SASL_SSL。
  • SASL —— SaslHandshake v1 + SaslAuthenticate v2；PLAIN、SCRAM-SHA-256/512（纯 MoonBit PBKDF2）、OAUTHBEARER（用户提供的令牌提供者）；支持重新认证。
  • 集群层 —— ClusterClient 统一管理引导集合、按节点 id 的连接池、带刷新调度的元数据缓存、topic-id 映射（KIP-516）、批量 FindCoordinator v4（KIP-699）。

阶段 2 —— 协议完备（数据面） 已完成

  • 版本协商矩阵 —— 逐 API 的下限/上限矩阵；握手解析 broker 区间为 BrokerVersions 存于每个连接；选择最高共同版本，无重叠时清晰报错。
  • Metadata —— v12/v13 按协商版本分发；暴露 topic_id（Fetch v13+ 需要）；DescribeTopicPartitions v0 游标分页；解码器边界检查加固。
  • Produce —— v12/v13（topic-id，KIP-516）；逐记录 record_errors 携带消息（KIP-467）。
  • Fetch —— v12–v16；增量 fetch 会话（KIP-227）含会话失效/重建；截断批次的显式处理（records_complete）。
  • ListOffsets v10/v11 —— KIP-1075 超时、KIP-1023 哨兵；公开偏移量哨兵常量。
  • 记录层 —— 记录头往返；详细批次解码（producer id/epoch、control/transactional 标志）；collect_committed read_committed 原语；RecordBatchBuilder。
  • 压缩 —— 统一 Codec 接口映射属性位 0–4；snappy/lz4 纯 MoonBit，gzip 经系统 zlib FFI，zstd 经内嵌解压库；来自独立实现的 golden fixture。
  • 解码器健壮性 —— 对压缩流、记录批次和五个线解码器做确定性模糊测试：只允许解码错误或成功，绝不 panic。

阶段 3 —— 完整生产者 已完成

  • 分区器 —— Murmur2（默认）、Murmur2RoundRobin、RoundRobin；按批次的粘性分区（KIP-794）；手动指定分区。
  • 批处理累加器 —— 每分区队列；batch_size 轮换、linger_ms 就绪、buffer_memory 记账（BufferExhausted）；合并发送时保持分区顺序。
  • Sender 任务 —— 每生产者一个排空循环；按 leader 分组、流水线在途上限（默认 5）；acks=0 免应答；可重试失败回到队首并按 delivery_timeout_ms（默认 120s）退避重试。
  • 公共 API —— send、逐记录 SendHandle（await/cancel）、批量 send_all、异步 on_complete 回调。
  • 幂等 —— InitProducerId v5；pid/epoch + 每分区序列号；UNKNOWN_PRODUCER_ID 时按 Java 客户端规则重置；配置校验（acks=-1、max_in_flight ≤ 5）。
  • 事务 —— 协调器初始化；begin/commit/abort_transaction；AddPartitionsToTxn v3；AddOffsetsToTxn v4 + TxnOffsetCommit v4；EndTxn v5 带纪元晋升（KIP-890）；协调器重试/重寻、栅栏检测、失败时需中止的提交策略。
  • 生产者指标 —— metrics()：队列深度、在途批次、发送/失败计数、限流提示。

阶段 4 —— 完整消费者 已完成

  • 偏移量管理 —— OffsetCommit v8–v10 / OffsetFetch v8–v10；commit/commit_async/committed 带协调器重试；seek 系列；后台自动提交含关闭前提交。
  • Fetcher —— 每 leader 并发长轮询 + 增量会话；max_poll_records/max_partition_fetch_bytes 上限与回退；暂停/恢复；auto_offset_reset 策略；KIP-320 截断检测（OffsetForLeaderEpoch v4）；read_committed 过滤。
  • KIP-848 成员 —— ConsumerGroupHeartbeat v0/v1；客户端生成成员 id；服务端驱动分配围绕 RebalanceListener 原子生效；静态成员；正则订阅（glob 子集）；优雅退出；栅栏恢复。
  • 经典组成员 —— JoinGroup v9 / SyncGroup v5 / Heartbeat v4 / LeaveGroup v5；Range、RoundRobin、Sticky 与 CooperativeSticky（KIP-429 两轮）分配器；静态成员；再均衡监听器。
  • 消费者 API 面 —— subscribe/assign 互斥；position/committed/assignment/group_metadata；max_poll_interval_ms 强制；utf8 记录辅助方法。
  • group_protocol 配置 —— KIP-848（默认）、经典、或按 broker 通告 API 探测回退。已记录互操作注意事项：混合厂商协作组、glob 正则子集、经典路径 UNSTABLE_OFFSET_COMMIT。

阶段 5 —— Admin 客户端 已完成

  • Admin 核心 —— 共享的可重试结果重试策略；任意 broker 控制连接 vs 控制器路由；逐项错误码以值返回；DescribeTopicPartitions 分页游标遍历。
  • 主题操作 —— CreateTopics v7、DeleteTopics v6（按名字/ID/混合）、CreatePartitions v3、DeleteRecords v2、OffsetDelete v0。
  • 集群/配置 —— DescribeCluster v0–v2、DescribeConfigs v4、IncrementalAlterConfigs v1 + AlterConfigs v2、ListConfigResources v0–v1（KIP-1142）、DescribeLogDirs v2–v5、ElectLeaders v2、分区重分配、UnregisterBroker v0、DescribeQuorum v2、UpdateFeatures v2。
  • 消费组 —— DescribeGroups v6（仅经典组）、ConsumerGroupDescribe v1（KIP-848 成员）、ListGroups v5、DeleteGroups v2。
  • 生产者/事务 —— DescribeProducers v0、DescribeTransactions v0、ListTransactions v2。
  • 安全 —— Describe/Create/DeleteAcls v2–v3（枚举字节值取自 Java 源码）；配额 Describe/AlterClientQuotas v0–v1；Describe/AlterUserScramCredentials v0（从口令派生 SCRAM 凭证）。

阶段 6 —— 共享组（KIP-932）与遥测 已完成

  • ShareConsumer —— ShareGroupHeartbeat v1 成员关系；ShareFetch v2（获取/释放语义、投递计数上限）；ShareAcknowledge v2（accept/release/reject/renew）；共享组偏移量的 Describe/Alter/Delete admin 操作。
  • 遥测（KIP-714） —— GetTelemetrySubscriptions/PushTelemetry 客户端 + 可插拔指标提供者。

阶段 7 —— 加固、性能与发布 已完成

  • 测试设施 —— Docker compose（KRaft 单/多 broker）、make integration、进程内模拟 broker testkit（限流、版本上限、SASL/TLS、会话翻动等故障注入）。
  • CI —— GitHub Actions：构建 + 测试、fmt 检查、moon info 干净差异、Docker Kafka 4.3 集成任务、golden 文件再生成。
  • 性能 —— 编码器预分配、近零拷贝解码（BytesView）、基准脚本与 bench-produce。
  • 文档与发布 —— README 特性矩阵、协议笔记、CHANGELOG，版本升至 0.2.0 并附发布检查清单。

测试策略

  1. 单元（纯函数） —— 编解码往返用 debug_inspect 快照测试；已知向量测试（murmur2、CRC32C、varint、SCRAM）；解码器健壮性（截断必须报错，绝不 panic）。
  2. Golden 文件 —— test/golden/ 中的字节级请求/响应 fixture；解码器必须能解析，编码器在确定性场景下必须字节一致。
  3. 模拟 broker —— 用 MoonBit 编写的进程内假 broker，说真协议：版本上限、错误注入、限流、会话翻动。
  4. 集成测试 —— Docker 化的 apache/kafka:4.3.x（KRaft），覆盖各阶段验收标准。
  5. 遵循 AGENTS.md：每次提交运行 moon info && moon fmt 并审查 .mbti 差异；阶段末审查覆盖率。

风险与待解问题

  • AddPartitionsToTxn v4/v5 形态 —— KIP-890 重塑了该 API；已通过探明 Java 4.x 生产者协商版本解决（客户端形态 v3）。
  • zstd 经 C FFI —— 已解决：内嵌 zstd 单文件解压库；gzip 链接系统 zlib。
  • moonbitlang/async 成熟度 —— 心跳/发送循环等长生命周期后台任务的取消语义；模拟 broker 测试覆盖高负载下的关闭。
  • 经典 vs KIP-848 特性差异 —— 经典组的正则订阅在客户端侧展开，与 848 的服务端正则不同；做文档说明而非强行统一。
  • SCRAM 纯 MoonBit 加密 —— 已验证：moonbitlang/x 提供 sha256/sha512 + HMAC，SCRAM 只需约 15 行 PBKDF2 循环，无需 C FFI。
  • 客户端 CSPRNG（成员 id） —— 已用时钟种子 uuid-hex 方案解决。
  • Kafka 4.3.x 小版本更新 —— 可能提升 API 上限；协商矩阵使其无感，但 golden 文件应随小版本再生成。
